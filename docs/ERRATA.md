# 协议勘误与文档缺陷记录

在实现本库的过程中，将 `memotalk-ble-skill` 的 4 份 reference 与真机抓包逐条对照，发现以下问题。**本库以抓包实测为准，不以文档描述为准。**

---

## E1 · `0xB0` 休眠超时示例帧的 CRC 错误

**影响（已由真机修正）**：该帧的 CRC 值确实有误，但固件 206 **不校验 CRC**，因此直接使用该帧在真机上**仍能成功执行**（实测返回 `5A 04 B0 01 84 01`，且设置实际生效）。实际风险在于：任何执行 CRC 校验的第三方实现，或未来加严校验的固件，都将拒收该示例帧。

> 该条最初记为「直接使用该示例帧会被拒绝」，真机回归否定了这一判断，此处已更正。详见 [HARDWARE-REGRESSION.md](HARDWARE-REGRESSION.md) 与下文 E8。

**文档位置**：`01-BLE-PROTOCOL-SPEC.md` 5.9 节第 561 行。

**文档给出**：

```
设为 300 秒 = 0x012C：5A 06 B0 00 2C 01 C7 90
```

**实测结论**：对 body `06 B0 00 2C 01` 计算 CRC16：

| 实现 | 结果 | 小端发送 |
| :-- | :-: | :-: |
| 厂商 nibble 查表法 | `0xC057` | `57 C0` |
| 独立位运算 CRC-16/ARC（poly 0xA001，init 0xFFFF） | `0xC057` | `57 C0` |

两种独立实现一致，均**不是** `0xC790`。

**正确帧**：

```
5A 06 B0 00 2C 01 57 C0
```

**已排除参数笔误**：穷举全部 65536 个 2 字节小端参数值，唯一能产生 CRC `0xC790` 的是 `0xCBD9` 秒（52185 秒 ≈ 14.5 小时），远超协议自身规定的 `15 ~ 7200` 上限。因此这是 CRC 笔误，而非参数笔误。

同批次其它 `0xB0` 示例均正确（`B0 01 2C 01 06 00`、`B0 02 01 C1 AF`、`B0 02 00 00 6F`），属孤立笔误。

本库按 `57 C0` 生成，见 `tests/test_codec.py::WriteCommandTests::test_write_setting`。

## E2 · 「21 条指令」的计数与实际不符

**文档位置**：`SKILL.md` 多处、`VERSION.md`。

**实际**：

- 可发送指令 **22 条**（14 读 + 8 写）
- 设备推送 **2 条**（`0xA8`、`0x90`）
- 异常应答 **1 条**（`0x00`）
- 合计 **25 个协议码**

`SKILL.md` 第二节表头写「写入与控制类（共 9 条）」，但表内只有 **8 行**，表头与表格数量不一致。

本库以 `tests/test_codec.py::CoverageGuardTests` 固定「22」这一数字，后续任何遗漏都会导致测试失败。

---

## E3 · 「内置后台保活器」在代码中不存在

**文档位置**：`SKILL.md` 第 92 行「…`0x84` 音频流重组器与后台保活器」。

**实际**：`scripts/ble_core.py` 中没有任何保活类、协程或定时器，只有可复用的 `cmd_read_battery()`。`macos_verify_cli.py` 也没有心跳循环。

**后果**：按文档直接使用的应用会在 300 秒无操作后被设备深度休眠并断开连接，必须手动按键唤醒。

本库在 `transport.py` 中以 `_keepalive_loop()` 补齐，并在文件传输期间自动暂停（`activity()` 上下文）。

---

## E4 · `0x07` 是悬空编号

**文档位置**：`01-BLE-PROTOCOL-SPEC.md` 第 139 行，把 `0x01 ~ 0x07` 整体列为「读取命令」。

**实际**：`0x07` 从未定义，无帧格式、无解析、无构建函数，文档中不存在对应章节。

**处理**：本库不实现。若真机存在该指令，可用 `client.raw.request()` 探测。

---

## E5 · `0x13` 文件列表「总长度」字段语义模糊

**文档位置**：`01-BLE-PROTOCOL-SPEC.md` 4.12 节。

**问题**：注释为「整个文件列表响应的总长度」，但未说明是否含每包 4 字节包头，也未给出单包完成与多包完成的判定条件。

**反推**：空列表帧 `FF 00 05 13 00 00 30 0D` 的长度字段为 `0x0005`，而实际帧长 8 字节，说明该值**不是**整帧长度。

**本库处理**：不依赖该字段做完成判定，改为「**解析出的条目数 == 声明条目数**」即完成（`FileListAssembler._try_parse`）。单包、多包、空列表三种情况统一处理，且不受该字段歧义影响。

---

## E6 · `0x84` ack 的变长字段与定长字段边界未说明

**文档位置**：`01-BLE-PROTOCOL-SPEC.md` 5.3 节。

**问题**：ack 为「应答 + 文件状态 + **变长文件名** + 错误码 + 3B 总包数 + 同步结果」，原 SDK 用 `pkt[-6:-3]` / `pkt[-3]` 取值，隐含「尾部定长」假设，但从未说明文件名如何与尾部字段分界。

**本库处理**：明确从尾部反推——`op = pkt[-3]`、`total = pkt[-6:-3]`、`err = pkt[-7]`、`name = pkt[4:-7]`。以真机样例（`5A 28 84 01 … 00 00 02 0D 00 7A F5`）验证：`total_packets = 525`、`op = START`；且本库构造的同名 ack 尾字节与真机一致。

## E7 · 多平台宣称与实际实现不符

**文档位置**：`SKILL.md` 第 9 行称支持「macOS/Windows/Linux/iOS/Android/微信小程序/Web」。

**实际**：

- `find_or_retrieve_device()` 的「已连接外设找回」依赖 bleak 私有属性 `scanner._backend._manager.central_manager`，仅 `darwin` 分支，属非公开 API。
- `wifi_fast_transfer_demo.py` 的入网使用 `networksetup -setairportnetwork`，**仅 macOS**。

**本库处理**：macOS 私有路径隔离在 `discovery._retrieve_connected_macos()` 内并整体 `try/except`；`NetworkSession.join_hotspot()` 在非 macOS 上明确抛 `CapabilityUnavailable`，不静默失败。

## E8 · 固件 206 **不校验 CRC，也不校验长度字段**（真机实证）

这是真机回归中最重要的发现，严重程度高于前述所有条目。

| 实验 | 发送内容 | 设备反应 |
| :-- | :-- | :-- |
| 读电量 + 双字节 CRC 全异或 | `5A 03 01 3F 7F`（CRC 错） | **正常应答** `5A 04 01 08 30 57` |
| 写休眠超时 600s + CRC 错 | `5A 06 B0 00 58 02 CF 3E` | **返回 success，且 600s 实际写入**（读回 600） |
| 长度字段改错 | `5A 05 01 C0 80`（声明 5，实际仅 3 字节体） | **正常应答**电量 |

**结论**：`0x5A` 帧的 CRC16 在该固件上不具备实际约束力，未提供任何完整性保护。

**风险**：蓝牙链路上的位翻转，或客户端组帧错误，都可能被设备**静默执行**。对 `0xB0` 表现为配置写入错误；若同样的宽容度作用于 `0x9A`（清空全部），单次错误帧即可能删除全部录音。

> `0x9A` 在 CRC 错误时的行为未作测试：该操作不可逆，涉及用户数据。上述判断基于 `0xB0` 的实测结果推断，并非实测结论。

**对本库的影响**：库仍然生成**数学上正确**的 CRC，并对**收到**的每一帧做校验。此校验并非多余：设备发出的帧 CRC 均正确，校验可拦截传输错误。

## E9 · 文档描述的 `0x00` 异常帧在固件 206 上**从未出现**

`01-BLE-PROTOCOL-SPEC.md` 3.1 节定义了 6 种错误码（超时/长度/校验/禁止操作/无效命令/无效参数）。真机逐项触发后：

| 触发条件 | 文档预期 | 真机实际 |
| :-- | :-- | :-- |
| CRC 错误 | `0x00` + `0x02` | 无视 CRC，**照常执行** |
| 长度字段错误 | `0x00` + `0x01` | **照常应答** |
| 未定义指令 `0x77` | `0x00` + `0x04` | **无任何应答**（超时） |
| 热点期间发起录音 | `0x00` + `0x03` | **无任何应答**（超时） |
| `0x84` 请求不存在的文件 | `0x84` ack 且 `exists=0x00` | **会应答**，但尾部只有 3 字节（见 E11） |

**结论**：该固件的失败语义是**无应答**，而非错误帧。

**对本库的影响**：`MemoTalkTimeout` 才是实际的错误信号，`DeviceErrorResponse` 分支在本固件上不可达。因此：
- `_call` 的超时值不宜过短（热点操作的实测响应时间可能超过 14s）；
- 捕获 `MemoTalkTimeout` 时必须考虑「操作可能已经成功，仅应答丢失」的情况。

**仍未验证**：`0x92` 删除失败确实返回了文档中的帧 `5A 05 92 00 04 A0 C6`（错误码 `0x04` 文件不存在），与文档字节一致。因此「无应答」并非普遍现象：删除类失败会返回应答帧。

## E10 · `0x87` 热点存在**过渡期锁**，中断 enable 会使设备短暂拒绝全部写入

**现象（真机复现一次）**：在某次 `wifi.enable()` 进行中（连接在过渡期被关闭）之后：

1. 随后两次 `0x87` 开启，均超时（超时设为 14s 仍无应答）；
2. `0x87` 关闭返回 `state=0 result=0`（成功=0，即失败）；
3. `0x03` 读 FTP 地址返回 `0.0.0.0`（热点确实已关）；
4. 但 **`0x80` 录音被拒绝**（`result=0x00`），设备仍处于快传模式判定；
5. 心跳读取（`0x01`）始终正常，说明链路未断开，是设备内部状态机停留在中间状态。

**自愈**：未作任何干预，约数十秒后自行恢复，录音立即可用。

**结论**：`0x87` 的状态切换是一个**有过渡窗口的异步过程**，在窗口内：
- `0x87` 不应答；
- `0x80` 被拒绝；
- 但这些都不产生任何错误帧（见 E9）。

**对本库的影响**：`wifi.session()` 的 `finally` 关闭必须容忍超时并重试；调用方不应将 `enable` 超时等同于「热点未开启」。已在 `HARDWARE-REGRESSION.md` 记录为已知限制。

## E11 · `0x84` 成功/失败应答的**尾部布局不同**；`0x13` 尾两字节不是 CRC16

两项均只能在真机上观察到。

### 1. `0x84` 有两种尾部

| 情况 | 帧结构 | 实测样例 | 帧长 |
| :-- | :-- | :-- | :-: |
| 文件存在 | `5A len 84 01 <name> [err] [3B BE 包数] [op] CRC` | `5A 28 84 01 …31B… 00 00 02 0D 00 7A F5` | N+11 |
| 文件不存在 | `5A len 84 00 <name> [status] [err] [op] CRC` | `5A 1B 84 00 …20B… 00 04 00 B6 00` | N+9 |

两种布局的 `op` 都在 `frame[-3]`，但失败帧没有 3 字节的包数字段。

**原实现的问题**：一律按成功布局切片，失败帧的文件名被截去 2 字节（`NOT_EXIST_000000.mp3` → `NOT_EXIST_000000.m`），包数被读成 `0x330000`（3342340），并抛出 `ProtocolError`。

**现在的实现**：先看 `exists` 位再决定切片（`parsers.parse_sync_ack`）。三种名字长度（6 / 20 / 34 字节）的真机帧全部解析正确，见 `tests/test_parsers.py::SyncAckTests` 与 `SimulatorFidelityTests`（后者强制模拟器输出与真机字节一致）。

**下游影响**：`AudioSyncAssembler.feed_ack()` 在失败应答时不再设置 `total_packets`（否则 `is_complete` 会立刻为真），`download()` 从而能够明确抛出 `FileNotFoundOnDevice`，而非 `ProtocolError` 或超时。

### 2. `0x13` 列表帧尾部的两字节不是 CRC16

同一段内容（空列表）三种取值：

| 来源 | 尾部两字节 |
| :-- | :-: |
| 协议文档 | `30 0D` |
| 真机固件 206 | `64 68` |
| 按 CRC16 实际计算 | `D5 09` |

三者互不相同，说明这两个字节**不是**内容校验和（相同内容应得到相同值）。

**影响**：任何对 `0x13` 帧做 CRC 校验的实现都会失败。

**本库处理**：`FileListAssembler` 从不对 `0xFF` 帧做 CRC 校验，只用标记位（`0x13`/`0x1D`/`0x2D`）+ 条目数判定完成。两种尾部都能正确解析（`tests/test_assemblers.py::SimulatorFidelityTests::test_both_empty_list_variants_parse`）。

## 校验方法

所有结论可复现：

```bash
python -m unittest discover -s tests -v      # 纯逻辑，无需硬件
python tools/selfcheck.py --out report.json   # 真机回归，需连接设备
```

`tests/test_parsers.py` 中的全部 hex 字面量均取自文档中的真机抓包；24 条中 23 条 CRC 自洽，唯一不自洽的是 E1 中的 `0xB0` 示例。
